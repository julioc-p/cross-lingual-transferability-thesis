\section{Experimental Setup}\label{section::experimental_setup}

\subsection{Data Processing}
The following data processing steps were applied to ensure the quality and relevance of the text queries:

\begin{enumerate}
    \item \textbf{Filtering Short Queries:}
    We removed all rows where the text queries contained fewer than four characters, as these were mostly errors originating from different datasets.
    
    \item \textbf{Classifying Statements vs. Queries:}  
    To distinguish between statements and valid queries, we employed the \textit{Gemma 27B IT model} \cite{team2024gemma} using its quantized 8-bit version to accommodate GPU memory limitations. We applied prompt engineering techniques to determine whether a given text was a statement rather than a query. If a query was classified as a statement (e.g., "The sky is blue"), it was removed from the dataset.
    
    \item \textbf{Initial Model Testing:}  
    Initially, we attempted to use \textit{BERT Large} for one-shot classification to differentiate between queries seeking information and nonsensical statements. However, this model struggled to reliably make this distinction.
    
    \item \textbf{Manual Filtering of Nonsensical Data:}  
    To further refine the dataset, we manually identified and removed commonly occurring nonsensical queries. Examples of such invalid queries include:  
    \begin{quote}
    \texttt{"not applicable", "redox is whom?", "Describe to me", "I have no idea", "does not apply", "ni idea"}
    \end{quote}
    
    \item \textbf{Translation and Expansion of the Dataset:}  
    For translation purposes, we used the \textit{Nous Research Model} \cite{teknium2024hermes} in 4-bit precision. This model was selected based on translation benchmarks, where it ranked among the best freely available models. Due to API limitations, we did not use commercial translation services such as Google Translate or DeepL, as they were not feasible for translating hundreds of thousands of data points.
    
    \item \textbf{Addition of German Data and Quality Filtering:}  
    The translation process added approximately 200,000 additional rows in the German language. However, we observed that longer translated queries often suffered from poor quality, requiring further filtering. For instance, some translations exhibited excessive repetition, as seen in the following example:  
    \begin{quote}
    "Hatte der Goldrausch Charlie Chaplin bearbeitet, geschrieben und für Charlie Chaplin, Charlie Chaplin Charlie Chaplin und Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie Chaplin Charlie ..."
    \end{quote}
    Due to such issues, we applied length-based filtering to remove problematic translations.

      \item \textbf{Generation of Contextual Entity/Relationship Mappings:} \label{item:context_generation}
    A key step for augmenting the dataset, particularly for English and German examples targeting Wikidata, and for preparing the input for the v2 model fine-tuning, was the generation of contextual entity and relationship mappings. 
    The goal was to provide the models with explicit Wikidata QIDs and PIDs corresponding to entities and relationships mentioned in the natural language questions, formatted as a JSON string.
    
    For an English question such as "Did United States Army employ a spouse of a character", the generated context would be:
    \begin{verbatim}
    {"entities": {"United States Army": "Q9212", "character": "Q95074"}, 
     "relationships": {"spouse": "P26", "instance of": "P31", 
                      "employer": "P108"}}
    \end{verbatim}
    Similarly, for a German question like "Hatte das United States Army eine Ehefrau eines Charakters eingestellt?", the corresponding German context, with localized keys, would be:
    \begin{verbatim}
    {"entitäten": {"United States Army": "Q9212", "Figur": "Q95074"}, 
     "beziehungen": {"Ehefrau": "P26", "Arbeitgeber": "P108", 
                     "Instanz von": "P31"}}
    \end{verbatim}
    This process leveraged large language models in a few-shot learning paradigm to extract these mappings by correlating the natural language question with its gold standard SPARQL query, which explicitly contains the QIDs and PIDs. 
    
    Two primary LLMs were employed for this task, selected based on their performance on public benchmarks (e.g., the Hugging Face LLM Leaderboard \cite{chiang2024chatbotarenaopenplatform}) and computational feasibility (models up to 70B parameters):
    \begin{itemize}
        \item For English examples: \textit{NousResearch/Hermes-3-Llama-3.1-70B} \cite{teknium2024hermes}.
        \item For German examples: \textit{meta-llama/Llama-3.3-70B-Instruct} \cite{grattafiori2024llama3herdmodels}. While the Hermes model showed strong performance in English, its German output for this task was found to be less reliable, prompting the use of the Llama-3.3 model for German, which demonstrated better results.
    \end{itemize}
    These operations were performed on NVIDIA A100-80GB GPUs.

    The models were prompted with a system message defining the task and the desired JSON output format, followed by one (for English) or three (for German) few-shot examples. An example of the system prompt used for English context generation is:
\begin{lstlisting}[breaklines=true, basicstyle=\ttfamily\scriptsize, frame=single, title=System Prompt (English Context Generation)]
You are a helpful assistant that extracts Wikidata entities and properties from SPARQL queries.
Output a valid JSON dictionary with no trailing characters. Format:
{
  "entities": {"ENTITY_LABEL_IN_QUESTION": "QID"},
  "relationships": {"RELATIONSHIP_LABEL_IN_QUESTION": "PID"}
}
Only use what you see in the SPARQL, no inferred knowledge. The labels in the JSON should correspond to how they are expressed or implied in the question.
\end{lstlisting}
    Each few-shot example consisted of a natural language question, its gold SPARQL query, and the target JSON output containing the entity/relationship mappings with natural language labels as keys. The model was then provided with the new question and its SPARQL query to generate the corresponding JSON mapping.
    
    The generated output from the LLM was validated for correct JSON formatting. If valid, the JSON string was added to a new `context` column in the dataset. This method was chosen for its pragmatic approach to leveraging existing gold SPARQL queries, rather than relying on more complex Named Entity Recognition (NER) and Relation Extraction techniques that might require separate model training.
    
    Through this process, 318,161 contextual annotations were generated for the training set (160,915 for English and 157,246 for German). Additionally, 784 context mappings were generated for the QALD-10 test set examples (English and German). While extensive manual verification of all generated contexts was not feasible, spot-checks indicated a generally high quality of mappings. The complete scripts and further details of this annotation process are available in the project's GitHub repository (see Appendix \ref{appendix:github_repository}).
\end{enumerate}

These preprocessing steps significantly improved the overall quality of the dataset by removing incomplete, irrelevant, and low-quality queries while expanding it with translated data and context.
\subsection{Training}
\subsubsection{Training Overview and Model Versions}

The fine-tuning experiments in this thesis centered on two primary base models: Mistral 7B v0.1 \cite{jiang2023mistral7b} and Occiglot-7b-eu5 \cite{avramidis-etal-2024-occiglot}.
The training process and the resultant fine-tuned models can be broadly categorized into two main iterations, designated as v1 and v2.
However, it is important to note that the development was an incremental process, with insights from earlier experiments informing subsequent refinements.

The v1 iteration itself comprised two sub-versions (v1.0 and v1.1), leading to a total of 10 distinct, functional fine-tuned models when considering all languages and variations throughout variations v1 and v2.
For clarity and conciseness, when "v1" is referenced throughout this thesis without further specification, it pertains to the final v1.1 models, which demonstrated slightly improved performance compared to v1.0 as will be described in this chapter.
The earlier v1.0 models and their configurations can be accessed through the commit history of the respective model repositories on the Hugging Face Hub (See Appendix \ref{appendix:v1_huggingface}).

The v1 set of experiments served primarily an exploratory purpose: to establish a baseline understanding of the general efficacy of fine-tuning these models for the text-to-SPARQL task with the dataset, and to identify initial challenges.
Consequently, the optimization was less of a focus in v1, particularly in the v1.0 stage which were only fine-tuned in English.

The v2 iteration was developed to address the limitations observed in v1 and to achieve higher performance.
A significant distinction was the incorporation of Wikidata entity and relationship ID mappings directly into the training input for the v2 models as context.
This approach was adopted not to supply them with the necessary explicit grounding for entities and relationships mentioned in the natural language queries.
The rationale was that if a model has not encountered specific token-to-ID mappings during its pre-training, it cannot be expected to generate them correctly.
Ideally, such mappings would have been part of the pre-training data; however, given the resource constraints of this thesis, providing them during fine-tuning and evaluation was an attempt to emulate the knowledge state of a model that had been pre-trained with this information.
This also allowed for an investigation into the hypothesis that the base Mistral model might have already been exposed to such mappings.
As will be discuss later, the performance increase (approximately fourfold in F1 score) suggest this exposure was likely minimal or incidental, something that cannot be asserted since by public statements from the Mistral AI team, the specifics of their training data are not disclosed due to the competitive nature of the field \cite{Arthurmensch_HF_MistralData_2023}.

Another key difference in the v2 experiments was the use of the base, non instruction-tuned versions of the LLMs.
This decision was made to allow for greater control over the input format, specifically to enable the inclusion of a custom system prompt for Mistral, as its instruction-tuned variant does not natively support it, and it was hypothesized that a well-crafted system prompt could guide the model more effectively during inference.
In contrast, the v1 experiments utilized the instruction-tuned versions of both models.

The v2 experiments also incorporated more best practices and advanced training techniques, such as an evaluation loop with the BLEU metric, early stopping criteria, NEFTune noise injection, and more targeted hyperparameter adjustments based on relevant literature, all of which will be detailed further in this chapter.

To ensure clarity and facilitate replication, the specific Hugging Face model identifiers used are as follows:
\begin{itemize}
    \item \textbf{v1 Experiments (Instruction-Tuned Models):}
    \begin{itemize}
        \item Mistral: \texttt{mistralai/Mistral-7B-Instruct-v0.1}
        \item Occiglot: \texttt{occiglot/occiglot-7b-eu5-instruct}
    \end{itemize}
    \item \textbf{v2 Experiments (Base/Raw Models):}
    \begin{itemize}
        \item Mistral: \texttt{mistralai/Mistral-7B-v0.1}
        \item Occiglot: \texttt{occiglot/occiglot-7b-eu5}
    \end{itemize}
\end{itemize}


\subsubsection{Computational Resources and Environment}

All model fine-tuning experiments were conducted on a High-Performance Computing (HPC) cluster provided by the German Research Center for Artificial Intelligence (DFKI).
The cluster offered access to a diverse range of NVIDIA GPUs, including A100, H100, and V100 models.
Due to high demand and consequently longer queue times for the A100 and H100 resources, NVIDIA V100 GPUs with 32 GB of GPU RAM were consistently utilized for all training runs to ensure timely and predictable access.
Each training job was allocated approximately 60 GB of system RAM, which proved sufficient for the chosen model sizes and batch configurations.

For simplicity and given that the model sizes were manageable on a single GPU, distributed training across multiple nodes or GPUs was not employed; all experiments were run on a single-node, single-GPU basis.
Job submission and management on the HPC cluster were handled using the Slurm Workload Manager.
The training environment was containerized using NVIDIA's Enroot container platform. The base Docker image for all training environments was \texttt{nvcr.io/nvidia/cuda:11.8.0-devel-ubuntu20.04}.
Within this containerized environment, all necessary Python libraries and dependencies required by the training scripts were installed using their latest stable versions available at the time of the experiments.


\subsubsection{Initial Fine-tuning}

To efficiently fine-tune the selected models within the available computational constraints, all experiments leveraged the Hugging Face ecosystem, particularly the Parameter-Efficient Fine-tuning (PEFT) library \cite{peft} and its integration of Quantized Low-Rank Adaptation (QLoRA) \cite{dettmers2023qlora}.
This integration implies the interplay of the BitsAndBytes, transformers, trl and peft libraries \cite{hf_blog_4bit_qlora_2023}.

The decision to employ 4-bit quantization was primarily driven by the 32 GB memory capacity of the V100 GPUs.
While both models require approximately 14-15 GB of GPU RAM in their native bfloat16 precision, loading the model, its optimizer states, and the training data batches for fine-tuning necessitates further memory optimization.
Quantization to 4-bit precision reduces the model's memory requirement substantially, allowing for the accommodation of larger batch sizes and longer sequence lengths, and ensuring that the training data vectors and gradients could fit within the GPU memory.

\textbf{Initial parameters (v1.0)}

The first fine-tuning experiments commenced with a set of baseline hyperparameters for the LoRA configuration and the general training arguments.

The initial LoRA setup was guided by a combination of values showcased in the hyperparameter search of the QLoRA paper \cite{dettmers2023qlora}.
The first choice of layers  (specifically, \texttt{q\_proj, k\_proj, v\_proj, o\_proj, gate\_proj, up\_proj, down\_proj, lm\_head}) was mainly driven by the huggingface community suggestions on finetuning Mistral 7B models like \cite{roggendorff2024finetuning}.
The configuration applied to the target modules was as follows:
\begin{itemize}
    \item \texttt{r} (LoRA rank): 64
    \item \texttt{lora\_alpha} (LoRA alpha, scaling factor): 16
    \item \texttt{lora\_dropout} (Dropout probability for LoRA layers): 0.1
    \item \texttt{bias}: "none"
    \item \texttt{task\_type}: "CAUSAL\_LM"
\end{itemize}

For the main training arguments, the initial settings were largely adapted from the parameters reported for the continual pre-training of the Occiglot models \cite{occiglot2024occiglot7b}, under the rationale that these had proven effective for adapting the base Mistral architecture.
However, significant adjustments were necessary to accommodate the single-GPU fine-tuning setup and the specific constraints of the available V100 hardware, particularly concerning batch size.
The key training arguments for the v1 experiments were:

\begin{itemize}
    \item \texttt{num\_train\_epochs}: 5
    \item \texttt{per\_device\_train\_batch\_size}: 1
    \item \texttt{per\_device\_eval\_batch\_size}: 1
    \item \texttt{gradient\_accumulation\_steps}: 8 (to achieve an effective batch size of 8)
    \item \texttt{gradient\_checkpointing}: True (to save memory)
    \item \texttt{optim}: "paged\_adamw\_32bit"
    \item \texttt{learning\_rate}: 1e-5
    \item \texttt{weight\_decay}: 0.05
    \item \texttt{bf16}: False (NVIDIA V100 does not support bfloat16 \cite{meng2024bfloat16})
    \item \texttt{max\_grad\_norm}: 1.0
    \item \texttt{max\_steps}: -1 (i.e., driven by \texttt{num\_train\_epochs})
    \item \texttt{warmup\_ratio}: 0.01
    \item \texttt{lr\_scheduler\_type}: "cosine"
    \item \texttt{group\_by\_length}: True (to optimize padding and speed up training)
    \item \texttt{max\_seq\_length}: None (allowing the model to handle variable sequence lengths up to its inherent limit, typically 2048 or 4096 tokens for these models)
    \item \texttt{packing}: False
    \item \texttt{device\_map}: \{"": 0\} (to ensure the model is loaded onto the primary GPU)
\end{itemize}

For the BitsAndBytes configuration for 4-bit quantization was set to dequantize for computations to float16.

A crucial adaptation from the Occiglot pre-training setup was the batch size.
Due to GPU memory limitations when fine-tuning the models, a \texttt{per\_device\_train\_batch\_size} of 1 was used. 
To compensate for this small physical batch size and simulate a larger effective batch size for more stable gradient updates, \texttt{gradient\_accumulation\_steps} was set to 8.

For these initial v1.0 fine-tuning runs, the full dataset (comprising nearly 900,000 examples) was not used.
Instead, for only English, a subset of 35,000 randomly sampled examples was selected for training.
This was done to expedite the exploratory phase and allow for quicker iteration cycles.
It is important to note that this training subset still contained a diverse range of queries originating from approximately 15 different knowledge graphs.
While SPARQL is a standardized query language, the specific entities, relationships, naming conventions, and structural query patterns can vary considerably across these different knowledge graphs.
This initial training took about 19 hours.

\subsubsection{Iterative Refinement and Observations}\label{sec:v1_iterations}

Following the initial v1.0 fine-tuning runs on the 35,000-sample English subset (which, as detailed in the last section, included data from approximately 15 knowledge graphs), several key observations emerged that guided subsequent refinements.

\paragraph{Initial Challenges: Knowledge Graph Ambiguity and Output Formatting}\mbox{}\\
A primary challenge observed in the v1.0 models was their difficulty in consistently generating SPARQL syntax appropriate for the specified target knowledge graph.
The input prompt for the Mistral model was structured as:
\begin{lstlisting}[breaklines]
Write a SparQL query that answers this request: <txt> from the knowledge graph <knowledge_graph>
\end{lstlisting}

For the Occiglot model, a system prompt was added to provide general guidance:
\begin{lstlisting}[breaklines]

System prompt: "You are an expert in SPARQL query generation. Generate the SPARQL query that answers the user's question"
\end{lstlisting}
Despite including the target \texttt{knowledge\_graph} in the prompt, when these v1.0 models were evaluated on the QALD-10 benchmark (which exclusively targets Wikidata), they often generated SPARQL queries incorporating \texttt{PREFIX} declarations or syntactic styles more characteristic of other KGs present in the mixed training data. 
For instance, none of the Wikidata queries in the training set utilize \texttt{PREFIX} declarations, yet the model would generate them, or use syntax more common to other knowledge graphs in the training set.
An example of such output, where the generated SPARQL for a Wikidata question included extraneous or misapplied prefixes and clauses, is shown below (raw model output often contained repeated query fragments and non-standard clauses):
\begin{lstlisting}[breaklines]
{
    "question": "What is the boiling point of water?",
    "knowledge_graph": "Wikidata",
    "generated_sparql_v1_0_mixed_kg": "SELECT ?obj WHERE { wd:Q283 p:P2102 ?s . ?s ps:P2102 ?obj . ?s pq:P459 wd:Q16523 }",
    "raw_answer_v1_0_mixed_kg": "SELECT ?obj WHERE { wd:Q283 p:P2102 ?s . ?s ps:P2102 ?obj . ?s pq:P459 wd:Q16523 } \nORDER BY DESC(?obj)\nLIMIT 1\nOFFSET 0\nCOMPACT \
PREFIX rdfs:<http://www.w3.org/2000/01/rdf-schema#> PREFIX rdf:<http://www.w3.org/1999/02/22-rdf-syntax-ns#> ..." 
    % Further prefixes and repeated query parts omitted for brevity
}
\end{lstlisting}
To extract the primary query from potentially noisy model outputs, a regular expression was employed:
\begin{verbatim}
import re
def extract_sparql(text):
    match = re.search(
        r"(SELECT|ASK|CONSTRUCT|DESCRIBE).*?\}", text, re.DOTALL | re.IGNORECASE
    )
    if match:
        return match.group(0).strip()
    return ""
\end{verbatim}
This regex targets common SPARQL query keywords and extracts content up to the first closing curly brace.

It seems this was the case since the loss was far stabler \ref{fig:loss_mistral_en_v1_0_1} and the rest of the parameters and the training set were left as is.
And the results for the QALD english test set show a slight improvement in generating executable queries going from 366 to 372.

\paragraph{Refinement 3: SPARQL Query Standardization} \mbox{}\\
Further analysis of the model outputs revealed a tendency to generate extraneous newlines, comments, and other non-executable artifacts within the SPARQL queries, as illustrated:
\begin{lstlisting}[breaklines]
{
    "question": "How many General Secretaries of the CPSU were there before Leonid Brezhnev?",
    "knowledge_graph": "Wikidata",
    "raw_answer_v1_0_wikidata_only": "SELECT ?value WHERE { wd:Q229728 p:P1037 ?s . ?s ps:P1037 wd:Q36769 . ?s pq:P1366 ?value} \n\nLIMIT 20 \n\nFILTER ( ?value < 1804-6-17 ) \n\nWORK BENCHMARK {\nbsd:0 P1306 ?value } \n\n#R 268 \n\n#sourceLanguage: en \n\n 34 \n\n 41 \n \n 58 \n\n 85 \n\n 111"
}
\end{lstlisting}
To address this, a SPARQL standardization step was incorporated into the data pre-processing pipeline for the training data. This step, applied to the entire $\approx 900,000$ example dataset, involved removing newlines and redundant whitespace from all SPARQL queries:
\begin{verbatim}
def standardize_sparql(query):
    query = query.replace("\n", " ")
    query = re.sub(r"\s+", " ", query).strip()
    query = re.sub(r'#.*', '', query).strip() 
    return query
\end{verbatim}
Interestingly, Occiglot models generally produced cleaner queries with fewer such artifacts compared to Mistral before these changes, potentially due to Occiglot's continual pre-training on code \cite{avramidis-etal-2024-occiglot} and the use of a system prompt during its fine-tuning.
However, this did not translate to a higher number of executable or correct queries for Occiglot in these early v1 iterations.

For the Mistral English model, the  \texttt{lm\_head} was removed from the target modules for LoRA.
The hypothesis was that the previously seen sensitivity from the training set might have been partially caused by the aggresive adaptation of the last linear layer of Mistral architecture mapping to the vocabulary space.
This, along with the standardization of queries and only using the knowledge graph Wikidata resulted in a marginal increase in the number of valid queries generated on QALD-10 (e.g., from 366 to 372 for Mistral English), though the number of correct answers remained unchanged at this stage. 

After these refinements, the generated queries were also visibly cleaner:
\begin{lstlisting}[breaklines]
{
    "question": "How many General Secretaries of the CPSU were there before Leonid Brezhnev?",
    "knowledge_graph": "Wikidata",
    "generated_sparql_v1_1": "SELECT ?value WHERE { wd:Q154569 p:P39 ?s . ?s ps:P39 wd:Q51471 . ?s pq:P155 ?value} ORDER BY DESC(?value)LIMIT 50"
}
\end{lstlisting}

\subsubsection{v2: Addressing v1 Limitations}\label{sec:v2_methodology}

The v1 experiments provided valuable initial insights and also highlighted critical areas for improvement, primarily the models' pronounced difficulty with accurate entity and relationship ID mapping for Wikidata. 
This section details the methodological enhancements and refined configurations adopted for the v2 fine-tuning iteration, which aimed to address these shortcomings and achieve superior performance.

\paragraph{The Entity Linking Bottleneck in v1} \mbox{}\\
A consistent observation across all v1 model variants was a significant deficiency in mapping textual entities and relationships to their correct Wikidata identifiers, despite often generating structurally valid SPARQL queries. 
For instance, evaluation of v1 Mistral English models on the QALD-10 test set revealed a macro recall score of approximately 0.069 (see example evaluation summary below). 
A substantial portion of the queries classified as "correct" achieved this status because both the generated query and the gold standard query correctly returned an empty result set, rather than through accurate data retrieval (5 of 27 correct matches).
\begin{verbatim}
--- Evaluation Summary (Example from v1.0 Mistral English on QALD-10) ---
Total Entries Attempted Evaluation: 391
Correct (Exact Match)             :   22 (  5.63%)
Correct (Both Empty)              :    5 (  1.28%)
Incorrect (Gen Empty, Gold Not)   :  248 ( 63.43%)
Incorrect (No Overlap)            :  110 ( 28.13%)
...
Macro Recall:     0.06905371
Macro F1-Score:   0.06905371
--------------------------
\end{verbatim}
The hypothesis that guided the changes in this version of the model was that this low recall mainly driven by the models' inability to correctly link entities.
For example, an early v1.0 Occiglot English model, when prompted with "Was Google founded by Bill Gates?" (targeting Wikidata), generated:
\texttt{ASK WHERE \{ wd:Q95 wdt:P112 wd:Q2283 \}}.
While correctly identifying Google (\texttt{wd:Q95}) and the "founded by" relationship (\texttt{wdt:P112}), it erroneously mapped "Bill Gates" to Microsoft's Wikidata ID (\texttt{wd:Q2283}). 
Similarly, an early v1.0 Mistral English model for "Was Lionel Messi Italian?" produced:
\texttt{ASK WHERE \{ wd:Q5421 wdt:P27 wd:Q38 \}}.
Here, the first ID (\texttt{wd:Q5421}) corresponds to the year 1233, not Lionel Messi. 
These mapping errors persisted across all v1 iterations, even after data standardization and cleaning efforts. 

\paragraph{Data Preparation and Prompting for v2} \mbox{}\\
Significant changes were implemented in data preparation and prompting for the v2 models:
\begin{itemize}
    \item \textbf{Base Model Selection:} The base (non-instruction-tuned) versions of Mistral 7B v0.1 and Occiglot-7b-eu5 were used. This decision facilitated the use of custom system prompts, which was hypothesized to be beneficial, in particular for Mistral, as its instruction-tuned version lacks native system prompt support.
    \item \textbf{Dataset Construction:} For each language (English and German), a dataset of 100,000 examples was randomly sampled (using a consistent seed of 42) from the master dataset. This was then partitioned into 80,000 examples for training, 10,000 for validation, and 10,000 for testing.
    \item \textbf{Prompt Formatting with Context:} The ChatML format \cite{openai_python_v0_28_0}, also utilized by Occiglot, was adopted for structuring the input. 
    Crucially, the system prompt for v2 models was designed to include the Wikidata entity and relationship ID mappings extracted for the given natural language query.
     An example of the input structure is as follows:
\begin{lstlisting}[breaklines]
[
  {
    "role": "system",
    "content": "You are an expert text to SparQL query translator. Users will ask you questions in English and you will generate a SparQL query based on the provided context enclosed in ```sparql <response_query>```.\nCONTEXT:\n{\"entities\": {\"Barnard College\": \"Q167733\", \"American\": \"Q30\", \"female\": \"Q6581072\", \"employee\": \"Q5\"}, \"relationships\": {\"instance of\": \"P31\", \"employer\": \"P108\", \"gender\": \"P21\", \"country of citizenship\": \"P27\"}}"
  },
  {
    "role": "user",
    "content": "Who was Barnard College 's American female employee"
  },
]

\end{lstlisting}
    The Hugging Face tokenizer was configured to apply this ChatML template to format the inputs appropriately for both Mistral and Occiglot models.
\end{itemize}

\paragraph{Revised LoRA Configuration for v2} \mbox{}\\
The LoRA configuration for v2 experiments was revised based on insights from v1 and further consultation of relevant literature:
\begin{itemize}
    \item \texttt{r} (LoRA rank): 256
    \item \texttt{lora\_alpha}: 128
    \item \texttt{lora\_dropout}: 0.05
    \item \texttt{target\_modules}: "all-linear" (targeting all linear layers, as recommended in QLoRA implementations \cite{artidoro_qlora_2023})
\end{itemize}
A higher LoRA rank (\texttt{r=256}) was chosen to provide greater model capacity for this complex generation task. 
The \texttt{lora\_alpha} was set to 128. 
It is worth mentioning that a common heuristic suggests \texttt{lora\_alpha} should be twice the rank \cite{Raschka2023PracticalTips}.
In this training the opposite is the case because of a mistake from the author which was found at the time of this writing.
It was maintained that way since the comparison between both models would still be fair. 
Comparisons between models are not confounded by this specific ratio choice, and the selected rank is within ranges explored in foundational QLoRA research \cite{dettmers2023qlora}. 
The \texttt{lora\_dropout} was adjusted to 0.05, a value found effective for 7B and 13B models in the QLoRA paper \cite{dettmers2023qlora}.


\paragraph{Revised Training Arguments for v2} \mbox{}\\
The general training arguments were also updated, drawing from best practices and the QLoRA paper \cite{dettmers2023qlora}:
\begin{itemize}
    \item \texttt{num\_train\_epochs}: 3. This was reduced from v1's 5 epochs, considering the larger 80,000-sample training set and indications from the QLoRA paper that further epochs yield marginal gains.
    \item Effective batch size: 6 (achieved with \texttt{per\_device\_train\_batch\_size=1} and \texttt{gradient\_accumulation\_steps=6}).
    \item \texttt{optim}: "adamw\_torch\_fused" was selected for potential training speed enhancements.
    \item \texttt{fp16}: True. This was enabled in the `TrainingArguments` to leverage mixed-precision for activations and gradients, which can improve throughput and reduce memory for these components, while the QLoRA setup managed the 4-bit precision of the base model.
    \item \texttt{learning\_rate}: 2e-4 (aligned with QLoRA paper settings for similar-sized models).
    \item \texttt{max\_grad\_norm}: 0.3 (aligned with QLoRA paper).
    \item \texttt{warmup\_ratio}: 0.03 (aligned with QLoRA paper).
    \item \texttt{lr\_scheduler\_type}: (aligned with QLoRA paper).
\end{itemize}

\paragraph{Enhanced Training Loop Features for v2} \mbox{}\\
To further refine the training process and model selection, the following techniques were integrated:
\begin{itemize}
    \item \textbf{Validation with BLEU Score:} A validation loop was incorporated, evaluating the models on the 10,000-sample validation set at regular intervals. The BLEU (Bilingual Evaluation Understudy) score \cite{papineni2002bleu} was employed as the evaluation metric. Given that text-to-SPARQL generation shares similarities with translation tasks (translating natural language to a formal language), BLEU was chosen as a practical proxy for generation quality. Real-time query execution against a SPARQL endpoint for validation was deemed too resource-intensive for frequent evaluation during training.
    \item \textbf{Early Stopping and Best Model Selection:} Early stopping with a patience of 3 was implemented based on the validation BLEU score. If the BLEU score did not improve for three consecutive evaluation checkpoints, training was halted. The \texttt{load\_best\_model\_at\_end=True} argument ensured that the model checkpoint corresponding to the highest validation BLEU score was saved as the final v2 model.
    \item \textbf{NEFTune for Regularization:} Noisy Embedding Fine-Tuning (NEFTune) \cite{jain2023neftunenoisyembeddingsimprove} was applied by setting a \texttt{noise\_alpha} value (5). NEFTune introduces noise to the embedding vectors during training, acting as a regularizer. This technique, though often highlighted for instruction tuning, was incorporated with the rationale that it could improve model generalization and mitigate sensitivity to the training data, an issue observed particularly with Mistral in v1 experiments, technique also explored by Yang et al. in a non uniquely instruction tuning context \cite{10.1145/3675249.3675339}.
\end{itemize}

\subsubsection{Challenges in v2 Model Output Generation}\label{sec:v2_output_challenges}

Despite the methodological enhancements in the v2 experiments leading to improved performance in SPARQL query generation (as will be detailed in Section~\ref{section::results}), a notable challenge emerged concerning the models' tendency to generate extraneous content after producing the target SPARQL query. 
This issue was observed for both Mistral and Occiglot.

While the v2 models often generated the correct SPARQL query structure and, with the provided contextual mappings, achieved significantly better entity/relationship ID accuracy than v1 models, their output did not consistently terminate after the query.
Instead, they would often continue generating text that resembled other examples from the training set, including new user prompts and assistant responses. 
An example from a v2 Mistral English model illustrates this (showing the full generated text after the prompt):
\begin{lstlisting}[breaklines]
{
  "question": "What did 1:42.08 's director and cinematographer direct , write , produce , executive produce , and edit",
  "generated_sparql_extracted": "SELECT DISTINCT ?x0 WHERE { ?x0 wdt:P57 ?x1 . ?x0 wdt:P1040 ?x1 . ?x0 wdt:P1431 ?x1 . ?x0 wdt:P162|wdt:P272 ?x1 . ?x0 wdt:P58 ?x1 . wd:Q208910 wdt:P344 ?x1 . wd:Q208910 wdt:P57 ?x1 }",
  "full_generated_text": "\n```sparql SELECT DISTINCT ?x0 WHERE { ?x0 wdt:P57 ?x1 . ?x0 wdt:P1040 ?x1 . ?x0 wdt:P1431 ?x1 . ?x0 wdt:P162|wdt:P272 ?x1 . ?x0 wdt:P58 ?x1 . wd:Q208910 wdt:P344 ?x1 . wd:Q208910 wdt:P57 ?x1 }``` toget\n pal/user\nWhat did 1:42.08 's cinematographer and director produce , write , edit , direct , and executive produce a film of George Lucas and LucasArts.edu:\n\n\
{\"entities\": {\"Star Wars: Episode I \\u2013 The Phantom Menace\": \"Q165713\", \"person\": \"Q5\"}, \"relationships\": {\"instance of\": \"P31\", \"director\": \"P57\", \"executive producer\": \"P1431\", \"writer\": \"P58\"}}t\nCharles Vidor\": \"Q149507\", \"actor\": \"Qx0\"}}4\ncharacters of the book Star Wars: Episode I \u2013 The Phantom Menace directed by , executive produced by , and written by a person that Charles Vidor was influenced by and was influenced by\n toget\n?:"
}
\end{lstlisting}
Although the primary SPARQL query within the \texttt{```sparql ... ```} delimiters was often correct and showed good performance metrics upon extraction, the subsequent extraneous generation was a persistent artifact. 
This issue was less pronounced in the v1 instruction-tuned models but became more apparent with the v2 base models, affecting both Mistral and Occiglot.

Initial investigations ruled out incorrect application of the ChatML template.
The core issue appeared to be the models' failure to consistently generate the End-Of-Sequence (EOS) token (e.g., \texttt{<|im\_end|>}) after completing the SPARQL query within the delimiters.

One hypothesis for the inconsistent EOS generation was the use of \texttt{packing=True} in the `SFTTrainer` arguments for the v2 models. 
Packing concatenates multiple short training examples into single sequences to improve training throughput by reducing padding \cite{kundu2024enhancing}.
However, this might inadvertently teach the model that EOS tokens within a packed sequence are not necessarily terminal for the overall generation context it is currently in, but rather just another token before the next packed example begins.

To test this, an experimental fine-tuning run (termed v2.1 for this investigation) was conducted for the Mistral English model with \texttt{packing=False}. 
For this specific run, LoRA parameters were also adjusted to align with those used for the 7B Guanaco model in the QLoRA repository (\texttt{lora\_r=16}, \texttt{lora\_alpha=32}) \cite{artidoro_qlora_2023}, maintaining the \texttt{lora\_dropout=0.05} and \texttt{target\_modules="all-linear"}. The rationale for ``lora\_alpha'' being twice `r` followed common guidelines \cite{Raschka2023PracticalTips}.
The model trained with \texttt{packing=False} (v2.1 Mistral English) exhibited a change in the nature of the extraneous output.
Instead of generating fragments of other training instances, it tended to produce repetitive phrases or statements related to the generated query itself after the closing ``` delimiters, as shown in the example below:
\begin{lstlisting}[breaklines]
{
  "question": "<|im_start|>system\nYou are an expert text to SparQL query translator. Users will ask you questions in English and you will generate a SparQL query based on \
the provided context encloses in ```sparql <respose_query>```.\nCONTEXT:\n{\"entities\": {\"Harz\": \"Q4186\"}, \"relationships\": {\"label\": \"rdfs:label\", \"language\": \"langMatches\"}}<|im_end|>\n<|im_start|>user\nHow is the Harz called in Mandarin Chinese?<|im_end|>\n<|im_start|>assistant\n",
 "gold_sparql": "SELECT DISTINCT ?result WHERE {wd:Q4186 rdfs:label ?result FILTER(langMatches(lang(?result),\"zh-cn\")) }",
  "generated_sparql_v2.1_packing_false": "SELECT ?answer WHERE { wd:Q4186 wdt:P1705 ?answer . ?answer wdt:P407 wd:Q15860220}",
  "full_generated_text_v2.1_packing_false": "\n```sparql SELECT ?answer WHERE { wd:Q4186 wdt:P1705 ?answer . ?answer wdt:P407 wd:Q15860220}``` &nbsp;\n?answer is the label for Harz in Mandarin Chinese. ?answer has the code wd:Q15860220. ?answer is the label for Harz in Mandarin Chinese. ?answer has the code wd:Q15860220. ..." 
  % Repetitions continue
}
\end{lstlisting}
This indicated that while `packing=True` might have contributed to the model "hallucinating" subsequent training examples, the fundamental issue of inconsistent EOS token generation after the structured SPARQL output remained.

In terms of performance for this v2.1 Mistral English (\texttt{packing=False}) model:
\begin{itemize}
    \item On the QALD-10 test set, the macro F1-score was slightly lower (0.215) compared to the primary v2 Mistral English model (0.250, trained with \texttt{packing=True} and \texttt{r=256, alpha=128}).
    \item On the custom 10,000-sample English test set (drawn from the same distribution as the training data), this v2.1 model achieved a slightly higher F1-score (0.863) compared to the primary v2 Mistral English model (0.827).
\end{itemize}
Despite the better performance on the test set with \texttt{packing=False}, the primary v2 models (trained with \texttt{packing=True} and the LoRA configuration detailed in Section~\ref{sec:v2_methodology}) were retained for the main comparative analysis presented in Section~\ref{section::results}. 
This decision was based on their superior F1-score on the more challenging and diverse QALD-10 benchmark, which is considered a more stringent test of generalization for this task. 
The extraneous text generation issue was managed post-hoc by extracting the content within the ```sparql ... ``` delimiters.

This investigation into output generation highlights the complexities of fine-tuning non instruction tuned LLMs for structured generation tasks and suggests that factors like dataset packing and EOS token generation warrant careful consideration in future work.

\subsection{Evaluation}

The performance of the fine-tuned text-to-SPARQL models developed in this thesis was assessed using a combination of custom-held-out test sets derived from the primary training data distribution and a standardized external benchmark.
All evaluations involved executing both the gold standard SPARQL queries and the model-generated SPARQL queries against the live public Wikidata SPARQL endpoint (\url{https://query.wikidata.org/}).
The results of these executions were then compared to determine query correctness and to calculate performance metrics.
Further details on the implementation of the evaluation script, \texttt{sparql\_validator.py}, can be found in the project's GitHub repository Appendix~\ref{appendix:github_repository}.

\subsubsection{Evaluation Datasets}\label{sec:evaluation_datasets}

Two types of datasets were employed for evaluating the fine-tuned models:

\begin{enumerate}
    \item \textbf{Test Sets:}
    For each iteration of models (v1 and v2) and for each language (English and German), dedicated test sets were created. 
    These were randomly sampled from the main multilingual dataset developed in this work (as described in Section~\ref{section::data_collection}) and were strictly excluded from any training or validation procedures to ensure an unbiased assessment of generalization to unseen data from the same general distribution.
    \begin{itemize}
        \item For the v1 models, the test sets comprised 3,500 examples per language.
        \item For the v2 models, which were trained on a larger dataset, the test sets were expanded to 10,000 examples per language.
    \end{itemize}

    \item \textbf{QALD-10 Benchmark:}
    To provide a standardized comparison against the broader field of Question Answering over Knowledge Graphs, the QALD-10 test set \cite{usbeck2024qald} was utilized as a key external benchmark. 
    The Question Answering over Linked Data (QALD) challenge series is a well-established competition in the field of Semantic Web, whose datasets are often used for evaluating systems that translate natural language questions into formal queries over knowledge graphs \cite{brei2024leveraging}. 
    QALD-10, the latest iteration at the time of these experiments, specifically focuses on Wikidata as the target knowledge graph and is notable for its multilingual nature, providing questions curated by native speakers in English, German, Chinese, and Russian, each paired with a corresponding gold standard SPARQL query \cite{usbeck2024qald}.

    The QALD datasets, and QALD-10 in particular, are recognized for their challenging nature, often featuring complex query structures and requiring nuanced understanding \cite{usbeck2019benchmarking}. 
    The decision to use QALD-10 was also influenced by related work, such as Brei et al. \cite{brei2024leveraging}, which highlighted its difficulty and used it to benchmark their systems.
    Its focus on Wikidata aligns with the training data used in this thesis, providing a relevant yet demanding test of the models' capabilities.
\end{enumerate}

The subsequent paragraphs will detail the specific metrics and procedures used to evaluate model performance on these datasets.

\paragraph{Initial Ad-hoc Metrics} \mbox{}\\
In the early stages of experimentation, particularly with the v1 models which exhibited lower initial performance, basic metrics were employed to gain a sensitive understanding of model learning. These included:
\begin{itemize}
    \item \textbf{Number of Executable Queries:} Counting how many generated SPARQL queries could be successfully executed against the endpoint without syntax errors or other execution failures.
    \item \textbf{Number of Exact Match Answers:} Counting instances where the set of results retrieved by the generated query was identical to the set of results retrieved by the gold standard query.
\end{itemize}
These simple counts provided an immediate signal of model improvement. 
For example, the baseline Mistral 7B Instruct v0.1 model (prior to fine-tuning for this task) when evaluated on the QALD-10 test set, produced only 34 valid (executable) queries and 3 correct answers out of 391 questions. 
After initial fine-tuning (v1.0 English), this improved to 366 valid queries and 23 correct answers, indicating that learning was occurring, even if overall correctness remained low. 
The "Executable Queries" metric was particularly useful as it offered a more granular view of progress when exact answer matches were still infrequent. 
An early overall summary looked like:
\begin{verbatim}
--- Evaluation Summary (Early v1 Example) ---
Total Queries Evaluated: 3500
Executable Queries: 2125 (60.71%)
Exact Match Answers: 163 (4.66% of total, 7.67% of executable)
Partial Match Answers: 1 (0.03% of total)
\end{verbatim}

\paragraph{Adoption of QALD Standard Metrics} \mbox{}\\
To align with established practices in the field, the evaluation methodology was then formalized using the QALD macro-averaged F1-score, precision, and recall, as described by Usbeck et al. (2019) and utilized in the QALD challenges (e.g., QALD-10).
The macro-F1 score is calculated as the average of the F1-scores for each individual question-answer pair.
The calculation of per-question precision (P), recall (R), and F1-score (F1) follows specific rules defined in the QALD benchmarking framework:
\begin{itemize}
    \item If the gold answer set is empty and the system also responds with an empty answer set, then P, R, and F1 are set to 1.
    \item If the gold answer set is empty but the system responds with a non-empty answer set, then P, R, and F1 are set to 0.
    \item If the gold answer set is not empty but the system responds with an empty answer set, the original QALD guidelines state that precision is set to 1, and recall and F1 are set to 0 (assuming the system determined it could not answer).
    \item In all other cases, standard precision, recall, and F1-measure are calculated based on the intersection and content of the retrieved answer sets.
\end{itemize}

\paragraph{Customizations and Refinements to Evaluation Metrics} \mbox{}\\
While adopting the QALD framework, a slight modification was implemented:
\begin{itemize}
    \item \textbf{Penalizing Non-Executable Queries:} If a model-generated SPARQL query was syntactically invalid or failed to execute on the endpoint for reasons other than a timeout (which was handled separately, see below), its precision, recall, and F1-score for that question were set to 0. This ensures that models are penalized for producing non-functional queries.
\end{itemize}
Furthermore, to gain more nuanced insights beyond the aggregate F1-score, the evaluation script was designed to categorize correct answers:
\begin{itemize}
    \item \textbf{Correct (Exact Match):} The generated query executes and retrieves the exact same non-empty set of results as the gold query.
    \item \textbf{Correct (Both Empty):} Both the generated query and the gold query correctly execute and return an empty result set. 
    This distinction helps to understand if high correctness is due to accurately identifying unanswerable questions or accurately retrieving specific data.
\end{itemize}
The evaluation summary provided by the \texttt{sparql\_validator.py} script incorporates these categories alongside other classifications like "Incorrect (Generated Empty, Gold Not)", "Incorrect (No Overlap)", and various failure types. 
An example of the final evaluation output format for a v1.1 Mistral English model on the QALD-10 test set is:
\begin{verbatim}
--- Evaluation Summary ---

\paragraph{Handling of Gold Query Execution Issues} \mbox{}\\
During evaluation against the live Wikidata SPARQL endpoint, it was observed that a small number of gold standard queries from the QALD-10 dataset consistently timed out or failed due to their complexity and the operational limits of the public endpoint. An example is the question "What event killed the most people in the years 1910 to 1920?", whose gold SPARQL query involves extensive path traversals. In this work, such questions for which the gold query could not be successfully executed on the live endpoint (3 instances in QALD-10) were categorized as "Ignored Question" and excluded from the metric calculations for all models. This decision was made to ensure a fair comparison, as evaluating generated queries against an unresolvable gold standard would be problematic. While hosting a local Wikidata instance could circumvent public endpoint limitations, utilizing the live endpoint was preferred to provide a more readily transferable and accessible evaluation framework for the research community.

The \texttt{sparql\_validator.py} script automates these calculations, including the set-based comparison of query results, and incorporates features such as multi-threading for parallel query execution, caching of results to speed up repeated evaluations, and retry logic to handle transient network issues or endpoint rate limits. 
This evaluation framework underpins the quantitative analysis presented in the next section.
